# Attendance Timesheet Crawler

GitHub-only attendance collection and report production for TimeMark / DaysCamera.

Production has one rule: **GitHub Actions is the only attendance producer and the only place that aggregates business report content.** Scheduled ChatGPT/Teams tasks are dumb consumers: they validate the GitHub state/artifact/report hash and publish the exact `teams_html` generated by GitHub. They do not read an attendance skill, do not open H5 links, and do not recalculate attendance.

## Production flow

```text
GitHub Secret: ATTENDANCE_ROSTER_JSON (exactly 8 employees)
  -> GitHub Actions queue
  -> wait until the required business snapshot time
  -> direct read-only attendance API for every employee
  -> Playwright/Chromium verification fallback where required
  -> normalize all attendance sessions
  -> validate durations/evidence
  -> build business report + Teams HTML inside GitHub
  -> encrypt raw + report payload
  -> publish state schema v3 with artifact ID + exact report file + SHA-256

Scheduled Teams consumer
  -> wait for matching current-date state v3
  -> download exactly that artifact
  -> decrypt it
  -> verify report SHA-256 and report contract
  -> publish report.teams_html unchanged
```

The attendance application is the source of punch evidence. GitHub Actions is the production execution and reporting layer. Teams timestamps, image-upload timestamps, normal work schedules, previous reports, previous runs, or previous artifacts must never be used to invent attendance times.

## Production schedule

GitHub cron is UTC; Vietnam is UTC+7 year-round. The producer is deliberately queued early so GitHub scheduler delay does not race the business reporting time.

| Purpose | Queue time VN | GitHub cron | Snapshot not before | Teams publication |
|---|---:|---|---:|---:|
| Morning | 11:55 | `55 4 * * *` | 12:15 | 12:30 |
| End of day | 20:30 | `30 13 * * *` | 20:50 | 21:05 |

There is **no 06:45 next-day reconciliation production schedule**.

If GitHub starts before the snapshot time, the job waits inside the workflow and collects only at/after the snapshot time. If GitHub starts late, it proceeds immediately. Consumers have a bounded wait window and fail closed rather than substituting stale data.

## Private roster

Production runtime roster comes only from the GitHub repository secret:

`ATTENDANCE_ROSTER_JSON`

Requirements:

- JSON array with exactly 8 employees;
- each item contains the employee name and original H5 URL;
- HTTPS only on `h5.timemark.com` or `h5.dayscamera.com`;
- exactly 8 unique `deviceId` values;
- employee order is stable and validated before report publication.

The scheduled consumer has **no runtime dependency on an attendance skill or H5 link list**. A stable identity fingerprint is used only as a guard against unintended roster identity drift.

## Collection strategy

The primary read-only endpoint discovered from the H5 application is:

```text
POST https://app.dayscamera.com/next/attendance/record/query/plain
```

For each of the 8 roster entries:

1. try the bounded direct API query;
2. if the target date cannot be safely established, perform browser verification;
3. use browser-observed structured API data when available;
4. use rendered DOM only as the final read-only fallback;
5. classify a technical failure separately from a genuine no-record result.

A direct-API miss is **not a missing link**. It is a source-selection state that may require browser verification.

## Session model

The crawler preserves **all valid sessions for the target date** in `sessions[]`.

This fixes a previous failure mode where reporting effectively retained only one morning session and one afternoon session, which could omit a third or later session.

Rules:

- every valid complete pair is preserved;
- duplicate/noisy contained punches are filtered using app duration evidence;
- open input or orphan output remains explicit and is never bridged to another session;
- a single continuous shift that crosses midday remains one valid shift;
- multiple sessions in the same period remain multiple sessions;
- total minutes are the sum of every trusted complete session, not merely two fixed buckets;
- duration mismatch beyond the accepted tolerance becomes `review_required` and is not manually recomputed.

The legacy `morning` and `afternoon` fields remain for compatibility, but production report totals use the complete `sessions[]` model.

## Raw attendance output — schema v5

The crawler writes:

```text
output/attendance-YYYY-MM-DD.json
```

Top-level contract:

```json
{
  "schema_version": 5,
  "date": "YYYY-MM-DD",
  "timezone": "Asia/Ho_Chi_Minh",
  "generated_at": "...",
  "employees": []
}
```

Each employee can contain `morning`, `afternoon`, `sessions`, `total_minutes`, source metadata, evidence, and a status such as `complete`, `incomplete`, `review_required`, `date_not_found`, or `technical_error`.

## GitHub-owned business report — schema v1

After the crawler succeeds, GitHub runs:

```bash
node scripts/build-report-payload.mjs
```

It creates exactly one report for the current slot:

```text
output/report-morning_1230-YYYY-MM-DD.json
output/report-daily_2105-YYYY-MM-DD.json
```

Contract:

```json
{
  "schema_version": 1,
  "kind": "attendance_business_report",
  "slot": "morning_1230",
  "date": "YYYY-MM-DD",
  "timezone": "Asia/Ho_Chi_Minh",
  "employee_count": 8,
  "employees": [],
  "quality": {},
  "teams_html": "..."
}
```

GitHub is responsible for all business interpretation used in the Teams report. The consumer is forbidden from modifying `teams_html` or recalculating rows from raw attendance data.

### Morning rules

- a valid `morning.in` without `morning.out` is `Đang làm việc`;
- lack of an afternoon session at 12:30 is not an attendance defect;
- `date_not_found` remains `⚠️ Chưa ghi nhận`, never an inferred absence;
- `technical_error` is `Không đọc được app`, never employee fault;
- `review_required` remains `Cần đối soát` and is not manually recomputed.

### End-of-day rules

- every trusted session in `sessions[]` is included;
- one complete cross-midday continuous shift is valid and is not marked as missing an afternoon shift;
- multiple sessions in a period are preserved and displayed;
- any open/orphan session makes the daily total `Chưa chốt`;
- the report never computes across a missing endpoint;
- technical/source states are not converted into employee noncompliance.

## Artifact security

The repository remains public, so attendance evidence is never committed as plaintext.

For every production payload:

1. GitHub creates a random per-run AES passphrase;
2. raw attendance JSON + GitHub-built business report are packed together;
3. the payload is encrypted using AES-256-CBC + PBKDF2 with 200000 iterations;
4. the random passphrase is encrypted with the committed RSA public key using RSA-OAEP SHA-256;
5. only the encrypted payload and encrypted session key are uploaded as the Actions artifact.

The corresponding private key is not committed to the repository and must never be logged or placed in Teams messages.

## Scheduled state — schema v3

A successful scheduled run updates only the matching state file:

```text
.github/attendance-state/morning_1230.json
.github/attendance-state/daily_2105.json
```

Current contract contains only routing/integrity metadata:

- `schema_version: 3`;
- run ID and run attempt;
- slot and target date;
- artifact ID and artifact name;
- roster/identity fingerprints;
- encryption marker;
- exact `report_file`;
- exact `report_sha256`;
- completion timestamp.

The state file contains no punch times, photos, addresses, locations, H5 URLs, or device IDs.

The `report_file + report_sha256` binding prevents a consumer from silently using another report or rebuilding a different interpretation.

## Scheduled consumer contract

The 12:30 and 21:05 consumers must do only the following:

1. reject duplicate successful Teams reports for the same date/slot;
2. wait for current-date state schema v3;
3. validate slot, target date, identity fingerprint, artifact ID/name, report path, and encryption marker;
4. download exactly the state artifact;
5. decrypt it without logging secrets;
6. hash the exact report file and require equality with `state.report_sha256`;
7. validate report schema v1, kind, slot, date, timezone, and exactly 8 employee rows;
8. send the existing `report.teams_html` unchanged;
9. fail closed with one short business-facing source-unavailable message if the bounded wait/gates fail.

The consumer must **not**:

- load an attendance skill;
- open employee H5 URLs;
- retrieve or reconstruct attendance links;
- derive punch times from Teams/images/schedules;
- read raw attendance in order to rebuild the report;
- recalculate durations or totals;
- substitute another date, run, artifact, or report.

## Test coverage

The Node test suite covers the existing parser/API rules plus report-level regressions, including:

- direct API request and Vietnam calendar-day boundaries;
- record deduplication;
- app duration conversion and mismatch fail-closed behavior;
- browser verification after direct API date misses;
- open sessions;
- morning sessions ending after noon;
- morning report not treating an absent afternoon as a defect;
- one continuous cross-midday shift remaining valid;
- preservation and totaling of a third session;
- end-of-day total blocked when any session is open;
- source-review states not being described as employee absence.

Run locally for development only:

```bash
npm install
npm test
```

Production attendance collection and aggregation remain GitHub-only.

## Privacy rule

Never commit real roster data, H5 URLs, device IDs, plaintext attendance results, screenshots, locations, or attendance photos to the public repository. Manual debug evidence, when explicitly enabled, must remain inside encrypted artifacts only.
